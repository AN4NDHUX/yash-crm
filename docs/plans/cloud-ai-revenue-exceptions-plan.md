## Problem Statement

CONVOSIS CRM should replace manual sales reporting with one auditable view of the complete Lead -> Visit -> Quotation -> Invoice -> Payment -> Incentive journey. Management must be able to see who is performing, who is close to target, where leads are stuck, which quotations need follow-up, which invoices remain unpaid, and who has earned an incentive. The AI layer must make this information easier to understand and act on without becoming the source of financial truth.

## Demand Evidence

No external demand validation has been established. No named manager, salesperson, committed pilot, paying customer, current-tool sequence, time cost, or observed reporting failure was supplied during office hours. The user repeatedly supplied desired product outputs, so the first release is a learning-oriented pilot rather than a validated production SaaS offering.

## Status Quo

The claimed status quo is manual reporting spread across lead assignment, conversations, follow-ups, visits, quotations, invoices, payments, targets, and incentive calculations. The exact tools, handoffs, data volumes, delays, error rates, and financial consequences remain unknown. The pilot must therefore expose its rules and collect manager corrections instead of encoding unverified workflow assumptions as autonomous behavior.

## Target User & Narrowest Wedge

The initial user is one named sales manager from one pilot company reviewing quotation follow-up. The first vertical slice is a browser-based **Today's Revenue Exceptions** view that deterministically identifies quotations needing follow-up, explains the triggering facts, and lets that manager approve one reversible action type: a Task assigned to the quotation owner.

The first pilot does not attempt to replace the entire CRM or automate every sales action. It proves whether one manager acts on a trustworthy quotation exception queue. Stalled leads, unpaid invoices, near-target performance, conversions, incentives, Calls, and Meetings are later slices that unlock only after the quotation slice meets the expansion thresholds.

## Constraints

- Use a free and open-weight model, not a paid proprietary model.
- Default to `openai/gpt-oss-20b:cheapest` through Hugging Face Inference Providers.
- Treat Hugging Face's free allowance as a small pilot quota, not unlimited production infrastructure.
- Do not use GPT-2 for CRM reasoning or structured action proposals.
- CRM users work entirely in the browser; no local AI server, PowerShell, Bash, or Python is required.
- The application database calculates targets, achieved amounts, achievement percentages, conversions, payment state, and incentives.
- The model may explain, prioritize, summarize, and draft reversible follow-up activities.
- The first slice permits only Tasks and requires explicit manager approval before creation.
- The pilot is single-company and single-approver. Shared HTTP Basic credentials cannot prove individual identity, so the approving actor is the configured administrator record and multi-user approval is prohibited until individual authentication exists.
- Quotation, invoice, payment, incentive, ownership, deletion, and other financial or irreversible mutations remain outside the first pilot.
- When inference is unavailable or quota is exhausted, the deterministic management view must remain usable.

## Premises

1. Recorded CRM data is the single source of operational and financial truth.
2. The first slice uses a deterministic, versioned rule to identify quotation follow-up. Additional exception families remain design targets, not first-slice claims.
3. The AI ranks and explains the deterministic exception set; it does not decide whether a financial or performance condition exists.
4. Missing conversations, visits, quotations, invoices, payments, or assignments are reported as missing data rather than inferred.
5. AI-generated Tasks are drafts until the named pilot manager approves them. Calls and Meetings remain disabled in the first slice.
6. Approval revalidates the single-company boundary, configured manager identity, quotation and owner state, due date, Task-only activity type, proposal version, and idempotency at write time.
7. The provider receives only the minimum fields required for the selected analysis.
8. The first pilot validates workflow usefulness before multi-user identity, multi-tenant SaaS infrastructure, additional exception families, or autonomous execution is built.

## Versioned Business-Rule Contract

### `quotation-follow-up/v1`

- **Clock:** pilot-company timezone configured before use; comparisons use its local calendar date. Until that setting exists, the feature remains disabled rather than silently using server time.
- **Included records:** active quotations in `Draft`, `Pending Approval`, `Approved`, or `Sent` status.
- **Trigger:** `valid_until` is missing, expired, or within seven local calendar days. The UI distinguishes each trigger rather than grouping them into one unexplained state.
- **Excluded records:** archived, accepted, rejected, expired, converted, cancelled, or superseded quotations; the pilot company must map any custom statuses before enablement.
- **Owner:** the quotation owner must be active. Missing or inactive ownership creates a data-quality exception and disables AI Task approval.
- **Amount at risk:** quotation amount is displayed as recorded and is never recomputed by the model.
- **Stable deterministic order:** expired first, missing validity second, nearest validity date third, then highest amount and oldest update timestamp. Record ID breaks final ties.
- **Missing-data outcome:** missing validity date or owner is shown explicitly and never inferred.
- **Rule version:** every exception and audit event records `quotation-follow-up/v1`.
- **Examples:** an open quote expiring today is actionable; an accepted quote is excluded; an open quote with no validity date is a data-quality exception; an open quote with an inactive owner is visible but cannot create a Task.

Later rule families must define the same fields: authoritative data, timezone and period, included and excluded states, missing-data behavior, boundaries, examples, and rule version. Incentive rules must also define reversals, cancelled payments, partial payments, reassignment, and period-close behavior before they can drive eligibility.

## Pilot Identity and Authorization Boundary

- One pilot company is the complete data boundary. The current schema has no tenant identifier, so unrelated-company data must not be loaded into the same deployment.
- One named manager is the only approver. The deployment's shared Basic credential is issued only to that manager for the pilot.
- The configured administrator `User` record is the actor written to approval and exception-review audit events.
- Salespeople may appear as record owners but do not receive approval access in slice one.
- Multi-user attribution, role-based manager access, object-level permissions, and multi-tenant isolation are not claimed and are mandatory before more than one approver or one company is onboarded.

## AI Data and Prompt-Injection Boundary

- The quotation analysis allowlist is: opaque proposal-local quotation reference, status, amount, currency if configured, validity date, owner reference, owner active flag, age, deterministic trigger, existing open Task intent keys, and rule version.
- Customer names, company names, notes, email bodies, attachments, arbitrary custom fields, credentials, phone numbers, and unrestricted free text are excluded by default.
- When a human-readable label is needed, it is resolved locally after the response. The provider does not need database record IDs that can be reused outside the response mapping.
- Untrusted CRM text is never placed in the system-instruction channel. Any future approved free-text field is delimited as data, length-capped, redacted, and covered by adversarial tests.
- The pilot company must accept the configured provider's retention and logging policy before enablement. If acceptable retention settings cannot be established, AI remains disabled and the deterministic queue still operates.
- The server rejects unknown local references, owners, activity types, fields, dates, extra actions, and records before a proposal reaches the approval UI.

## Ranking and Visibility Contract

- The complete deterministic exception set and count remain accessible at all times.
- AI may reorder presentation but cannot add, suppress, filter, merge, change severity, or alter exception membership.
- Managers can switch instantly to the documented deterministic order.
- Every AI-ranked row shows that the order is AI-generated, the ranking rationale, model identifier, and source rule version.
- The UI reconciles the AI-ranked count with the deterministic count; any mismatch rejects the ranked response and falls back to deterministic order.

## Exception Review Lifecycle

- States: `open`, `acted_on`, `dismissed`, `corrected`, and `unclear`.
- Only the named pilot manager may change state.
- `acted_on` requires a created Task ID or a short description of an external action.
- `dismissed` requires a reason and expires after seven days; if the deterministic trigger still applies, the exception reopens.
- `corrected` means the exception rule or source data appears wrong. It creates a non-mutating review record and link to the source record; it never changes a quotation, invoice, payment, incentive, owner, or other business record automatically.
- `unclear` requires a note and returns the item to product review.
- A source-record change reruns the deterministic rule. Resolved triggers close the exception; still-valid triggers retain or reopen it according to the state rules.
- Every transition records actor, prior state, new state, reason, timestamp, rule version, and source-record version.

## Proposal Idempotency and Approval State Machine

- The server issues an immutable proposal ID and integer version when an AI response is accepted for display.
- A proposal is bound to company deployment, source quotation, Task type, owner, deterministic exception ID, normalized intent, due-date window, and source-record version.
- A database uniqueness constraint covers proposal ID plus version. A second approval of the same version returns the original outcome.
- Editing a proposal creates a new version; older versions become stale and cannot be approved.
- Approval states are `received`, `validating`, `succeeded`, `rejected`, and `needs_reconciliation`.
- Receipt is durably recorded before validation. Activity creation and the `succeeded` transition commit in one database transaction.
- Terminal validation failures record `rejected` with a non-secret reason. A crash leaving `received` or `validating` is reconciled by checking the uniqueness key and activity linkage before retry or terminal classification.
- Stored provider metadata is limited to provider, model, provider request ID when available, token counts, latency, and error class. Prompts and raw provider responses are not retained by default.

## Success Criteria

- The deployed `/ai` page reports a configured Hugging Face connection without exposing the token.
- A hosted request against synthetic or approved redacted CRM data returns schema-valid structured analysis.
- `quotation-follow-up/v1` produces a deterministic, count-reconciled exception set and provenance for the first slice.
- Repeating the same query over the same record versions returns the same exception set and order.
- AI explanations cite source record identifiers and do not invent amounts, owners, activities, or records.
- Non-manager, stale, unknown, edited, and invalid Task approvals are rejected before an activity write.
- Double-clicks, retries, stale versions, and concurrent approvals produce at most one Task and return the same durable outcome.
- Every approval reaches a durable terminal state or `needs_reconciliation`; reconciliation never creates a second Task.
- Provider timeout, 401, 429, quota exhaustion, malformed output, and outage states show actionable browser errors while deterministic reporting continues to work.
- **Discovery gate:** one manager approves the rule contract and uses the deterministic quotation queue during one real review before AI expansion work is considered validated.
- **Pilot gate:** three managers use the queue for two weeks. At least 90% of reviewed exceptions are judged correctly triggered; at least 80% are understood without assistance; at least 30% result in an action; correction rate stays below 10%; duplicate or unsafe proposal rate is 0%; and the median review saves at least 20% versus a measured manual baseline.
- **AI-added-value gate:** at least 20% of acted-on exceptions use an AI-ranked position, explanation, or approved Task that managers rate as more useful than the deterministic view alone.
- **Iterate:** rule precision 75–89%, comprehension 60–79%, action rate 10–29%, or time saving below 20% triggers one rule/UI iteration without adding scope.
- **Stop:** rule precision below 75%, comprehension below 60%, any unsafe or unauthorized mutation, any cross-company data exposure, or no measurable time saving stops expansion and returns the product to deterministic-only operation.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — feasibility

**Problem**

> The identity boundary permits exactly one named approver using a shared Basic credential and explicitly prohibits multi-user approval, but the required pilot gate has three managers use the queue and measures their actions and ratings. The document neither limits the additional managers to read-only observation nor introduces individual identity before that gate, so it cannot safely attribute three managers' review states, approvals, or usefulness ratings under the committed pilot architecture.

**Remedy**

> Choose an executable sequence: either keep the success gate to the single authenticated manager, define the other two managers as supervised read-only evaluators whose feedback is captured outside product audit claims, or make individual authentication and per-manager audit attribution a dependency before the three-manager pilot begins. Align Constraints, Identity Boundary, Success Criteria, Dependencies, and the Assignment to that choice.

### R2-2 — consistency

**Problem**

> The exception lifecycle enumerates only open, acted_on, dismissed, corrected, and unclear, but later says resolved triggers close an exception. There is no closed or resolved state, no transition into it, and no rule for what happens to prior acted_on, corrected, or unclear review history when a source change removes and later recreates the trigger.

**Remedy**

> Define the missing resolved or closed state and a complete transition table driven by review actions, source changes, dismissal expiry, and trigger recurrence. Specify whether a recurring trigger reopens the same exception or creates a new occurrence while preserving the prior review and Task linkage.

### R2-3 — clarity

**Problem**

> The uniqueness constraint on proposal ID plus version makes retries of one displayed proposal idempotent, but it does not prevent two regenerated proposal IDs for the same exception, normalized intent, owner, and due-date window from creating duplicate Tasks. The document says proposals are bound to those logical fields but never makes that binding an atomic uniqueness scope, and it still gives no retention or expiry rule for deduplication records.

**Remedy**

> Define a canonical logical-operation key from the company deployment, exception occurrence, Task type, owner, normalized intent, and due-date bucket; enforce it atomically across proposal IDs where duplicates are forbidden. State when a distinct follow-up is allowed, how edits affect the key, and how long proposal outcomes and deduplication keys remain authoritative.

### R2-4 — clarity

**Problem**

> The first slice calls Task creation reversible and promises to show the exact mutation, but it never defines the allowed Task payload, server-owned versus model-drafted fields, content and length constraints, due-date calculation, or how an approved Task is reversed when deletion and other mutations are outside the pilot. Rejecting unknown fields does not define the safe values of known fields.

**Remedy**

> Specify the first-slice Task schema and validation contract, including fixed activity type, owner rules, subject and description limits, permitted model-authored text, due-date boundaries, escaping and display behavior, and immutable source linkage. Either define an authorized cancel or archive path with audit behavior or stop describing Task creation as reversible.

### R2-5 — completeness

**Problem**

> The approval design says provider metadata has bounded retention but supplies no duration, deletion trigger, or relationship to the longer-lived approval and exception audit records. This leaves the prior audit-retention obligation unresolved and prevents the pilot company from approving a concrete data lifecycle.

**Remedy**

> Define retention periods and deletion behavior separately for proposal payloads, provider metadata, approval attempts and outcomes, exception-review events, deduplication keys, and reconciliation records. State which records must outlive the pilot for financial or security audit purposes and which are purged on a schedule.

### R2-6 — consistency

**Problem**

> The quotation rule says an expired valid_until date is an actionable trigger while also listing expired quotations among excluded records. A reader can infer that one means a date condition and the other a status value, but the contract does not say so, making the same word both included and excluded in a supposedly deterministic financial rule.

**Remedy**

> Distinguish field semantics explicitly: for example, include an allowed-status quotation whose valid_until date is before the local date, while excluding records whose normalized status equals Expired. Add an example covering that exact distinction and define precedence when status and date disagree.

### Prior finding evidence

**R1-4 → R2-2 (persisting)**

> Exception Review Lifecycle adds review states, permissions, reasons, expiry, non-mutating correction, and audit fields, but it says resolved triggers close an exception without defining a closed state or complete recurrence transitions.

**R1-9 → R2-3 (persisting)**

> Proposal Idempotency and Approval State Machine defines immutable IDs, versions, stale edits, retry outcomes, and proposal binding, but uniqueness remains proposal-ID-plus-version and therefore does not deduplicate regenerated proposals for the same logical Task; retention is also unspecified.

**R1-10 → R2-5 (persisting)**

> The approval state machine now durably records receipt, atomically commits Task creation with success, records rejections, and reconciles crashes, but the promised bounded provider-metadata and audit retention policy still has no concrete lifecycle.

#### Exception occurrence lifecycle

Persist an exception occurrence with states `open`, `acted_on`, `dismissed`, `corrected`, `unclear`, and `resolved`. Review actions change the state; a source update that removes the deterministic trigger sets `resolved` while preserving all prior events and Task links. Dismissal expires after seven days and reopens the same still-triggering occurrence. After an occurrence resolves, a later recurrence creates a new occurrence linked by source quotation and rule version; it does not overwrite the prior history.

Allowed transitions:

| Cause | From | To | Requirement |
| --- | --- | --- | --- |
| Rule first matches | none | `open` | Store source-record version and trigger facts |
| Manager approves Task | `open`, `unclear` | `acted_on` | Link the succeeded approval and Task ID |
| Manager dismisses | `open`, `unclear` | `dismissed` | Require reason and expiry timestamp |
| Manager reports bad data/rule | `open`, `unclear` | `corrected` | Require reason; do not mutate source record |
| Manager needs product review | `open` | `unclear` | Require note |
| Trigger ceases | any non-resolved state | `resolved` | Preserve previous state in transition event |
| Dismissal expires while trigger remains | `dismissed` | `open` | Same occurrence, new event |
| Trigger recurs after resolution | `resolved` | new `open` occurrence | Link predecessor occurrence |

#### Logical idempotency

Each proposed Task receives a canonical operation key derived server-side from deployment identity, exception occurrence ID, fixed activity type, owner ID, normalized intent code, and due-date bucket. A database uniqueness constraint covers this key across regenerated proposal IDs. Proposal ID plus version remains the retry key for the exact displayed draft. A new follow-up is allowed only after the prior occurrence resolves and a new occurrence is created, or when the manager explicitly chooses a different allowlisted intent and due-date bucket. The operation key is never model-authored.

#### Safe Task contract

- `activity_type`: server-owned constant `Task`.
- `related_type` and `related_id`: server-owned quotation linkage derived from the exception occurrence.
- `owner_id`: quotation owner at proposal time; approval rejects missing, inactive, or changed owners.
- `intent`: one of `quote_follow_up`, `confirm_validity`, or `resolve_missing_validity`.
- `subject`: server template selected by intent, maximum 160 characters; the model cannot supply arbitrary subject HTML.
- `description`: optional plain text drafted by the model, 1,000 characters maximum after normalization; render only through escaped text paths.
- `priority`: server-owned `High` for expired validity dates and `Normal` otherwise.
- `due_at`: server-calculated in the organization timezone, between the current local time and seven local calendar days; the model may suggest urgency but not a raw timestamp.
- `status`: server-owned `Open`.
- Reversal: because deletion is excluded, this release calls creation **cancelable**, not reversible. The approver may cancel the created Task through an audited Task status transition to `Cancelled`; cancellation never deletes history or reopens the source exception automatically.

#### Retention contract

| Data | Retention |
| --- | --- |
| Raw prompts and raw provider responses | Not stored |
| Displayed proposal payload and versions | 30 days after terminal approval state, then redact model-authored text while retaining hashes and links |
| Provider metadata and errors | 30 days |
| Approval attempts, terminal outcomes, exception transitions, Task links | 365 days minimum |
| Deduplication operation keys | 365 days minimum and never shorter than linked Task/audit retention |
| Reconciliation records | 365 days after terminal reconciliation |

Scheduled cleanup must be idempotent and must never remove a key needed to prove that a retained Task was created once. Pilot export or deletion requests must preserve the minimum security audit required by the deployment owner.

#### Expired terminology

An **expired validity date** means an allowed-status quotation whose `valid_until` is earlier than the organization-local calendar date; it remains an included exception. An **Expired status** means the normalized quotation status value equals `Expired`; that record is excluded. Status exclusion takes precedence when the status and date disagree. Example: `Sent` with yesterday's validity date is included; `Expired` with tomorrow's validity date is excluded.

### Error and rescue registry

| Failure | User-visible behavior | Rescue path |
| --- | --- | --- |
| AI token missing or disabled | Queue loads in deterministic order with an explicit setup badge | Configure cloud secret; no data or actions are lost |
| Provider 401/403 | Deterministic queue remains; show credential error without token content | Replace scoped token and retry ranking |
| Provider 429/free quota exhausted | Deterministic queue remains; show quota message and next safe action | Wait for reset or fund a provider; no automatic retry storm |
| Timeout/outage | Deterministic queue remains; ranking request ends within configured timeout | Manual retry; bounded single retry only for transient connect failures |
| Malformed or count-mismatched model output | Reject entire ranking and show deterministic order | Log error class/metadata, not prompt body |
| Stale quotation/owner/proposal | Approval is rejected before Task write | Refresh row and regenerate proposal version |
| Double click/retry/concurrent approval | Return original terminal outcome | Atomic operation-key uniqueness and transaction reconciliation |
| Crash during approval | State becomes `needs_reconciliation` if outcome is uncertain | Reconciler checks Task linkage and operation key before retrying |
| Missing/inactive owner | Exception remains visible but Task action is disabled | Correct source ownership outside AI flow |

### Failure modes registry

| Risk | Prevention and detection | Release gate |
| --- | --- | --- |
| Cross-company data exposure | Single-company deployment boundary; allowlisted payload; no tenant claims | Any exposure stops the pilot |
| Model changes financial truth | Model cannot define exception membership or write financial fields | Contract and adversarial tests must pass |
| Duplicate Task | Two-layer idempotency plus atomic uniqueness | Concurrency test must produce one Task |
